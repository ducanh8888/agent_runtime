# H4 — revision-pinned workspaces

Date: 2026-09-11 (Asia/Bangkok).
Implementation baseline: `5365e7b`.
Verified code revision: `52687b3` (this documentation/release record follows it).

## Outcome

H4 shipped in source: a conversation's workspace has a mode, and the two
non-shared modes pin the caller's own local commit instead of a fetched remote
tip. The candidate was not installed into the production daemon; H7 still owns
the one production cutover. The full suites have not been re-run for this phase
yet — see Verification.

## What shipped

- **Modes.** `shared` (the default, unchanged), `snapshot` for an immutable
  review tree, `isolated_worktree` for a writable writer. The legacy
  `worktree: true` flag maps onto `isolated_worktree`, so existing dispatches
  keep their behaviour.
- **Local pin.** `_prepare_request_workspace` no longer calls
  `_get_worktree_start_point`, which ran `git fetch origin` and based the tree
  on `origin/<default>` — a different revision than the one the caller
  reviewed, which is the defect H4 exists to remove. The new
  `resolve_local_commit` goes through the hardened read-only git runner, whose
  allowlist has no `fetch`. A snapshot is a detached worktree; a writer's tree
  keeps a branch because it is meant to advance.
- **Refusals instead of partial captures.** A repository with no commits, one
  with submodules, or one carrying Git LFS content is refused with a reason via
  `WorkspacePreparationError`. A snapshot must be evaluable; an incomplete
  capture presented as complete would be worse. A request for isolation that
  cannot be honoured is now an error rather than a silent no-op.
- **Dirty overlay, opt-in.** `workspace_dirty_overlay` copies the caller's
  modified, deleted and untracked files onto the pinned tree and records a file
  count, a digest and the capture window. Every file is hashed before and after
  the copy; one that changes is retried once and then refused. The recorded
  level says `verified-copy-not-atomic`, because it is not a point-in-time
  snapshot of a tree another process is writing. Dependency trees and caches are
  never copied.
- **Durability.** `workspace_mode`, `workspace_requested_ref`,
  `workspace_resolved_sha`, `workspace_prepared_at`, `workspace_capture` and
  `workspace_capture_detail` are persisted on the stored record and exposed
  through `ConversationInfo`. On resume, a pinned workspace that is missing, is
  not a repository, or (for `snapshot` only) is no longer at the pinned commit
  is refused — `start` otherwise creates the directory and `git init`s it, so a
  session would run against a fresh empty tree and report work against a
  revision nobody reviewed.
- **Isolation guarantees, tested.** Two writers get separate trees, and a commit
  in one appears in neither the other nor the source checkout. Re-preparing one
  conversation leaves another conversation's uncollected work in place.

## Remaining limits

- **A snapshot is revision-pinned, not write-protected.** Immutability rests on
  the permission preset and on path confinement; a session with a terminal can
  write anywhere it can reach. Real immutability needs an OS sandbox, which is
  explicitly out of scope for this plan.
- **The dirty overlay is a verified copy, not an atomic capture.** A file edited
  during the copy is refused, but a file edited between two files' copies is
  captured at two different instants. The record says so.
- **Worktree lifetime is not swept.** `/tmp/conversation-worktrees/<id>/` is
  replaced when the same conversation is re-prepared and otherwise left for
  inspection; nothing deletes it, which also means nothing deletes another
  session's uncollected work. There is no explicit cleanup verb.
- **Submodules and LFS are refused, not supported.**
- No live end-to-end run was part of this pass; the live gate remains an H7
  action alongside cutover.

## Rollback

H4 adds defaulted fields to `ConversationConfig`, `StoredConversation` and
`ConversationInfo`, so legacy records still load. The old `worktree: true`
caller keeps its behaviour. Source rollback is a normal revert of the H4
commits; do not run an older binary over state after a future migration.
