# H3 — waits, finalization and the reserved-summary policy

Date: 2026-09-11 (Asia/Bangkok).
Implementation baseline: `5365e7b`.
Verified code revision: `c0f4a7f` (this documentation/release record follows it).

## Outcome

H3 passed its source, regression and adversarial-review gates. The control
surface gained a blocking wait that mirrors a foreground sub-agent launch, and a
finalize verb that stops a run at a safe boundary and returns the outcome it
has. The reserved-summary policy is opt-in and off by default, so the legacy
`max_iterations` hard limit keeps its meaning for every session that does not
ask for it. The candidate was not installed into the production daemon; H7
still owns the one production cutover.

## What shipped

- **Waits.** `wait_any` / `wait_all` on the MCP surface, backed by
  `Client.wait`. Outcomes are grouped as `completed`, `partial`, `failed`,
  `stopped` (paused, resumable), `missing` (unknown or deleted) and
  `still_running`. A timeout returns the unfinished ids as `still_running` with
  `timed_out` true -- never as failures, and never with partial output
  presented as a final answer. Unknown ids are classified rather than waited
  on, so a wait for a deleted session does not wait forever.
- **No human-attention bucket.** Nothing in the surface means "someone must
  approve this". A confirmation pause is not a branch the caller must hand to a
  person; every outcome is one the orchestrator resolves itself.
- **Settled is not the first `finished`.** A session is reported settled only
  when its terminal execution status and its admission state agree *and* the
  same condition held on the previous sample. `finished` is provisional: a run
  can flip back to `running` for a stop hook or a message that arrived during
  its final step. Admission is checked so accepted-but-unstarted input is never
  reported as an outcome.
- **Finalization.** `finalize` (MCP tool, `POST .../finalize`, `Client.finalize`)
  lets the in-flight step reach a safe boundary and blocks further tool starts.
  It returns the same payload `result` does. The request is persisted against
  the consumed input, so repeating it returns the same outcome instead of
  re-running anything. It reports what is known rather than claiming rollback:
  an external effect already in flight may still be running.
- **Reserved summary is opt-in.** `AGENTRT_FINALIZE_SUMMARY` (default off)
  gates the tools-disabled wrap-up, and the per-request `summary` flag asks for
  it. When it runs it is charged to the run's remaining allowance and warns in
  the log before taking the final slot. When it cannot run -- disabled
  deployment-wide, no allowance left, or the provider call fails -- `summary`
  is absent and the partial record is returned, never a summary that does not
  exist.
- `ConversationInfo.finalized_at` and `AgentResponseResult.summary` report the
  finalization to a listing and to the answer. `conversation_router` and the
  MCP tool descriptions describe the shipped behavior.

## Review evidence and rejected claims

AgentRT session `5e30ed33` reviewed the change read-only (dispatched with the
`workspace` preset and read-only instructions; `artifacts` showed no repository
file written by it). It reported six findings; all six were accepted:

- **A later request inherited the previous request's summary.**
  `final_summary` was returned whenever it was set, so `send` after a finalize
  reported the old summary and timestamp for the new input. Fixed by scoping
  both `summary` and `ConversationInfo.finalized_at` to
  `finalized_request_id == consumed_user_message_id`, with a regression.
- **A terminal session with a newer unconsumed input settled as `completed`.**
  The server reports that case as terminal-but-admitted with `result_state:
  pending`, and the wait accepted it. `_is_settled` now also refuses
  `result_state == "pending"` (an old daemon that reports nothing is still
  accepted), with a regression.
- **Two concurrent finalize calls could both run the summary.** The claim is now
  taken under the state lock with no await in between, before the summary runs.
- **The barrier was a no-op while the status read `finished`.** `pause` does
  nothing in that state, and `finished` is provisional. Finalize now re-pauses,
  bounded to three attempts, and the result's own status shows a run that
  genuinely keeps going instead of claiming a stop.
- **`timed_out` was true on a successful early `wait_any`.** It now means the
  deadline ended the wait, as documented.
- **`wait` could overshoot its timeout** by a full interval plus request
  latency. The sleep is now capped at the remaining time.

The phase's own gates also caught three defects before or alongside review: the
mock state in `test_h2_request_scope.py` lacked the new fields the projection
now reads (six tests failed loudly rather than diverging silently); an earlier
draft returned `final_summary` without the boundary check above; and
`_compose_conversation_info` passed `finalized_at` both through the persisted
state dump and as an explicit keyword, which raised `TypeError` on every create
and search path. That last shape is the second occurrence of the same mistake --
H2 hit it with `iterations_used` -- so a new state field that the projection
also passes explicitly must be dropped from the dump.

## Remaining limits

- **The wait is a poll, not a push.** The orchestrator drives it, unlike the
  native sub-agent whose completion arrives as a notification. The surface is
  therefore identical in shape but not in mechanism, and each wait costs one
  status request per id per interval.
- **Cross-suite test isolation.** `tests/sdk/conversation/local/test_execute_tool.py`
  defines a `Tool` subclass in the test module and leaves it in the process-wide
  registry; a later OpenAPI export in the same pytest process then fails with
  "Local classes not supported". This predates H3 and is not caused by it --
  run each suite as its own command, which is what the repository's checks do.
- **The TypeScript client is still not regenerated** (inherited from H2): the
  fork's OpenAPI export script imports the pre-rename `openhands` namespace.
  The new fields and `response`'s nullability are not reflected there.
- **A provisional `finished` is only narrowed, not closed.** Finalize re-pauses
  up to three times, but a stop hook that keeps denying the stop can still take
  another step afterwards. The result's own `status` reports that run as
  running, so the caller is not told it stopped when it did not.
- **The reserved-summary warning is a log line**, not a protocol signal; an
  orchestrator cannot see it before the slot is spent.
- `finalize` marks the request as finalized even when the summary could not
  run, so the recorded outcome is the partial record. It does not retry.
- No live model run was part of this pass; the live multi-tool gate remains an
  H7 action alongside cutover.

## Rollback

H3 adds defaulted fields to `ConversationState` and additive fields to existing
response models, so legacy state fixtures still load and parse. Source rollback
is a normal revert of the H3 commits. Do not install or restart an older binary
over state after a future phase introduces a migration.
