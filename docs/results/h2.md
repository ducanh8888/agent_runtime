# H2 — request-scoped results, errors and progress

Date: 2026-09-11 (Asia/Bangkok).
Implementation baseline: `29d87c5`.
Verified code revision: `0288eff` (this documentation/release record follows it).

## Outcome

H2 passed its source, regression and adversarial-review gates. A conversation's
answer, error, last completed tool and progress are now scoped to the newest
user input a run actually consumed, instead of the last answer anywhere in the
log. Explicit titles persist at creation; result and admission state are
reported separately from execution status. The candidate was not installed into
the production daemon; H7 still owns the one production cutover.

## What shipped

- **Boundary in the SDK.** `ConversationState.consumed_user_message_id` records
  the newest user `MessageEvent` the current run stepped on, written at all four
  step sites (async native, async ACP, sync) and reset per run along with
  `iterations_used`. A run may consume several inputs and one input may take
  several runs; the answer belongs to inputs up to the boundary only.
- **Bounded extraction.** `get_agent_final_response(events, *, after_id=...)`
  considers only events strictly after the boundary. A boundary that is not in
  the log returns no text rather than crossing an unknown scope.
- **Derivation** (`agent_server/run_scope.py`): `result_state` is
  `pending`/`final`/`partial`/`unavailable`, `admission_status` is
  `queued`/`preparing`/`admitted`, and `iterations_remaining` is derived from the
  run's allowance.
- **Projection.** `GET .../agent_final_response` returns the state, a nullable
  `response` (null when pending -- never the previous answer), the boundary id,
  iterations used/remaining, the last completed tool (any observation, including
  an errored one), the last persisted event time as durable progress, and the
  sanitized current-request error. Pending and unavailable results carry no
  error, tool or progress, so a previous request's failure is never shown as
  this one's.
- **Listing.** `ConversationInfo` carries `result_state`, `admission_status`,
  `iterations_used` and `iterations_remaining`, derived from persisted state
  alone, so a listing costs no event-log read.
- **Explicit title at creation.** `StartConversationRequest.title` is persisted,
  and auto-titling is not scheduled for a session that already has a title. The
  runtime had been sending `title` to a schema that silently dropped it.
- **Runtime/MCP/CLI.** `status`, `result` and `transcript` expose the scope,
  sanitized errors and action ids/paths/ranges (`transcript` previously dropped
  error events entirely, making a failed session look like a clean stop). MCP
  `dispatch` accepts `tags`; the CLI accepts repeated `--tag KEY=VALUE`; the MCP
  tool descriptions describe the shipped behavior.

How the phase's own Done criteria map to tests, and what is not covered:

- *send after finish/error* and *multiple pending inputs*: the boundary-projection
  tests assert that a newer input is `pending` with a null response, and carries
  no error, tool or progress from the previous request.
- *resume* and a second run: the SDK integration test sends, runs, sends again,
  runs again, and asserts the boundary advances and the counter resets.
- *process crash and reload*: state serialization tests plus the legacy fixture
  load, which assert the new fields default and persist.
- *golden legacy fixtures still load*: the `v1_11_5_cli_default` fixture.
- *not covered by a live model run*: no dispatched end-to-end session was run
  during this pass, so a real provider completion was not exercised. The server
  suite and the SDK run-loop tests are deterministic substitutes; the live
  multi-tool gate remains an H7 action, alongside cutover.

## Review evidence and rejected claims

AgentRT evidence session `57d31746` reviewed the change read-only (dispatched
with the `workspace` preset and read-only instructions because the running
production daemon predates the `inspect` preset; `artifacts` confirmed it wrote
no file). It reported six findings. Five were accepted and fixed with a
regression each:

- a pending request was shown the previous request's error, tool and progress;
- the ACP boundary pointed at the ACP prompt id, which can name an environment
  stop-hook feedback message rather than a user input;
- `iterations_used` was not reset when a run continued after a confirmation
  pause, so the reported budget could appear to grow;
- a recorded boundary missing from the event log was reported as a `final`
  empty answer instead of `unavailable`;
- `last_completed_tool` ignored errored observations, so a failed last tool was
  reported as an older successful one.

The sixth (the committed TypeScript client still types `response` as
non-nullable) is recorded as a limitation below rather than fixed here.

The phase's own regression caught one defect before review: `ConversationInfo`
was given `iterations_used` both by the state dump and as an explicit keyword,
which raised `TypeError` in `_compose_conversation_info` and broke every create
path.

## Remaining limits

- **The TypeScript client is not updated.** `clients/typescript/...` still types
  `response` as `string` while the wire now sends `null` for pending. It was not
  regenerated because this fork's OpenAPI export script imports the pre-rename
  `openhands` namespace; the Python runtime/MCP is the only consumer in this
  deployment. Regenerate or update it before any TypeScript consumer is used.
- Scoping depends on the persisted state and the event log agreeing. A boundary
  that is not in the log is reported `unavailable`; provenance is never
  invented.
- The ACP boundary uses the newest real user input; an ACP step that consumes an
  older queued prompt while a newer user message waits would overstate the
  scope. The native path (this deployment) is exact.
- `pending` and `unavailable` results carry no progress or error, so a caller
  must read `state` before treating the fields as current.
- Legacy sessions report `unavailable`; their last answer is returned, but it is
  not attributed to a request.
- H2 is complete in source only. The installed production runtime remains the
  pre-H1 build until the H7 migration/rollback gate.

## Rollback

H2 adds defaulted fields to `ConversationState` and additive fields to existing
response models, so legacy state fixtures still load and parse (exercised by the
`v1_11_5_cli_default` fixture). Source rollback is a normal revert of the H2
commits. Do not install or restart an older binary over state after a future
phase introduces a migration.
