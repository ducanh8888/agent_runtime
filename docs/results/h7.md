## One hazard the cutover produced

After the client reconnect, two daemons were found running against the same
state directory: the one this cutover started (port 40785) and a second the
reconnected MCP server had spawned (port 42985, and what `daemon.json` then
recorded). The plan forbids exactly this — two daemons must never write one
state directory — so the older process was stopped and the newer kept, after
confirming no session was running. The MCP call that had timed out on
`daemon.lock` succeeded immediately afterwards.

It is worth recording as a shape rather than an incident: `daemon start` is
idempotent only against the port recorded in `daemon.json`, so a daemon started
by a different route (here, the CLI during the cutover) is invisible to the next
client that decides to start one. Nothing detected the duplicate on its own.

## The sub-agent items (H7.9) and the H5 sub-item

Four items that were outstanding when the cutover was recorded are now done,
each with regressions and narrow-suite evidence:

- **Context inheritance** ships as `dispatch_from(session, task)`: it forks
  another AgentRT session and gives the fork the task, so a reviewer can start
  from the writer's history rather than from a summary of it. The daemon cannot
  read the orchestrator's own conversation, so that is where this stops; the
  fork inherits the source's agent, workspace and permission, and its docstring
  says so.
- **A stall signal, reported and not acted on**: the answer now carries
  `progress_age_seconds`, the time since the last persisted event. No automatic
  abort was implemented, and that is a decision rather than an omission: the
  orchestration notes measured a session that read its inputs and produced
  nothing for five minutes while composing a single response, so silence is not
  stalled-ness and a watchdog that killed on it would discard work that was
  about to land.
- **Progress visibility in the wait surface**: `still_running` items carry the
  last sampled status, admission, result state and iteration counts, so a
  poller sees movement without a second call. They still carry no result:
  partial output is never presented as an answer. A pushed completion remains
  impossible over the stdio transport and is not attempted.
- **The H5 shared-writer limit**: `AGENTRT_MAX_SHARED_WRITERS` caps how many
  running sessions may write in one workspace directory, counted from live run
  tasks and only for AgentRT-managed sessions; `capacity` reports the limit and
  the busiest directory, and `shared_writers` becomes the limiting dimension
  when it binds. Editors and unrelated processes in that directory never
  participated in this and still do not.

## Remaining before H7 can be called complete

- **Staged scale verification.** No 50–100 worker run has been attempted, and
  the load, window and host-pressure thresholds have to be agreed before one is.
- **The client-side MCP reconnect is a user action.** The stdio MCP servers
  running inside existing orchestrators hold the old code in memory and may
  also hold the old daemon port from before the cutover; a restart of those
  orchestrators is what loads the new surface. This session's own MCP server is
  one of them, which is why the new tools are not callable from here.

## Rollback

The pre-cutover backup is
`/home/ducanh/.agentrt-backups/pre-h7-20260912-002127/state.tar.gz`. Rollback is
to stop the daemon, restore that archive over the state directory, and reinstall
the revision it was taken from. Do not run the old build against a state
directory that a later migration has mutated; the backup exists precisely so
that this is never necessary. Work created after the cutover must be reconciled,
not deleted — the backup does not contain it.
