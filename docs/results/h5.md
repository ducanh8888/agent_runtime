# H5 — durable admission and dispatch-many

Date: 2026-09-11 (Asia/Bangkok).
Implementation baseline: `52687b3`.
Verified code revision: `bad3374` (this documentation/release record follows it).

## Outcome

H5's core shipped in source: a saturated run pool queues accepted work instead
of refusing it, the queue survives a restart, submissions can be keyed, and a
batch submission is validated once and returns per-item outcomes. Two planned
sub-items are deliberately not implemented and are listed under Remaining
limits. The full suites have not been re-run for this phase yet.

## What shipped

- **Capacity is backpressure, not refusal.** When no run slot is free, the
  input is persisted and the conversation is recorded as `admission_state:
  queued`; a scheduler admits it, oldest submission first, as slots free. The
  caller submits once and collects later instead of re-dispatching rejects.
- **Admission is decided and started under one lock**, so two dispatches cannot
  both take the same last slot. The running count is measured from live run
  tasks rather than from a counter, so a crashed or finished run cannot leak a
  slot — the two ways a slot counter goes wrong are excluded by construction
  rather than by careful bookkeeping.
- **Recovery.** The queue is rebuilt from the persisted records on start
  (`_rebuild_admission_queue`, ordered by `admission_enqueued_at`), so work
  accepted before a restart is admitted after it.
- **Capacity surface.** `GET /api/conversations/capacity`, `Client.capacity`
  and the MCP `capacity` tool report `running`/`limit`/`available`, the queue
  length and `limiting_dimension`. A disabled cap (zero or negative) is
  reported as unbounded: `limit` and `available` are null, because there is no
  ceiling to subtract from and a numeric remainder would read as a small one.
- **Submission idempotency.** `idempotency_key` on the create request,
  `Client.dispatch` and MCP `dispatch`. The same key with the same submission
  returns the conversation the first call created; the same key with a
  different submission is refused with 409. The fingerprint covers the
  workspace, title, tags, iteration cap, workspace mode and initial message,
  and deliberately excludes the conversation id (a retry uses a fresh one), the
  agent and the secrets.
- **dispatch-many.** `Client.dispatch_many` and MCP `dispatch_many` validate
  every item before creating any, bound the batch, and return `accepted` and
  `failed` lists with a reason per failure.
- **Queued cancellation.** Stopping or deleting a queued conversation drops it
  from the queue and writes the persisted admission state back, so it cannot
  start on its own later; an explicit resume still runs it.

## Remaining limits

- **Provider/account/model request-slot accounting is not implemented.** The
  cap is on runs, not on in-flight LLM requests, and nothing is tracked per
  provider account. A run holds its slot between LLM calls. This is the largest
  gap against H5's specification and it needs a deployment-level limiter on the
  LLM call path, which this pass did not build.
- **Shared-workspace writer limits are not implemented.** H4 gives writers
  separate worktrees; a limit on writers sharing one workspace does not exist.
- **Retry/backoff is per LLM call only** (the SDK's existing tenacity policy).
  There is no server-side retry or backoff for admission itself; a failed
  admission attempt is simply retried on the next scheduler tick.
- **Scheduling is FIFO by submission time.** A large batch is not starved by a
  later small one, but a small batch submitted after a large one waits behind
  the earlier items; there is no weighted or per-caller fairness.
- **Cross-process admission is not atomic.** The gate is an in-process lock,
  which is correct for the single-process daemon this deployment runs. A
  multi-process daemon would need the existing conversation lease, and that is
  not demonstrated.
- The scheduler polls (`admission_poll_seconds`, default 2 s), so a queued
  conversation can wait that long after a slot frees.
- No live end-to-end run was part of this pass.

## Rollback

H5 adds defaulted fields to `ConversationConfig`, `StoredConversation` and
`ConversationInfo`, so legacy records still load. A conversation that was
`queued` under H5 and is read by older code simply has an extra field. Source
rollback is a normal revert; do not run an older binary over state after a
future migration.
