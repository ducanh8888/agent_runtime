# H6 — attachments, cache visibility and complete accounting

Date: 2026-09-11 (Asia/Bangkok).
Implementation baseline: `87b0d30`.
Verified code revision: `304776f` (this documentation/release record follows it).

## Outcome

H6 shipped in source: images can be attached to a dispatch and are guarded,
per-session usage is readable from MCP and the CLI, a session's totals survive
its own deletion in a lifetime ledger, pricing is versioned and refuses to
guess, and first-token latency is recorded separately for reasoning and for
visible content. The candidate was not installed into the production daemon; H7
still owns the one production cutover.

## What shipped

- **Attachments.** `dispatch` on the client, MCP and CLI takes image paths, which
  become a typed `ImageContent` block on the initial message. The server model
  already accepted image content; nothing on the dispatch path produced it. The
  guards: the path must resolve inside the workspace and pass the credential
  alias check every other reader goes through; the format is sniffed from the
  file's own bytes (PNG, JPEG, GIF, WebP), because an extension is the caller's
  claim and the MIME is what the provider acts on; a 5 MB cap, refused with the
  size in the message.
- **Vision is required, and said so.** A dispatch whose worker model has no
  active vision capability is refused with 422 rather than sent: the provider
  would drop the image and the session would answer confidently about something
  it never received. The check runs on every creation path, not only when a
  deployment LLM policy is configured, because it is about the message.
- **Usage is readable where the orchestrator is.** `usage` is a client method, an
  MCP tool and a CLI subcommand, over the existing REST projection. Its
  description says how to read the payload: raw counts are the provider's own,
  the normalized view is derived beside them, and an unrecorded field is
  unavailable rather than zero.
- **A lifetime ledger.** A session's per-model token totals are folded into
  `<state_dir>/spend_archive.json` before its directory is deleted, so deleting
  a session cannot silently lower a lifetime total. This is the defect the
  friction log recorded: 73 deletions took the reported figure from about $0.84
  to about $0.39 with no money coming back. `DELETE
  /api/conversations/spend-archive` is the only operation that lowers the total,
  and it is not part of any cleanup. Only token counts are stored.
- **Versioned pricing.** `tools/spend.py` prices from a table whose entries carry
  a version and a source, prices per model from the per-call records rather than
  per session, and reports a model the table does not cover as a token count
  instead of charging it at another model's rate. Running it here showed why:
  about 8.7M tokens belong to models the table does not cover.
- **First-token latency.** `Metrics` keeps a `FirstTokenLatency` per call, for the
  first reasoning token and the first visible token separately, recorded at the
  streaming loop and attached to the call when the response id is known. The
  usage projection exposes both in milliseconds; a record written before the
  field existed reads as null -- unknown, not zero.

## Review evidence and rejected claims

AgentRT session `c0b49d37` reviewed the phase read-only. It reported six
findings; all six were real and all six are fixed in `304776f`, each with a
regression. Two were severe:

- **Archived spend priced as $0.00.** `cost_for` read short key names while the
  ledger stores the full ones, so every archived model priced as zero. The live
  path was correct, which is exactly what made it dangerous: the one number the
  ledger exists to preserve was the one it got wrong.
- **First-token timing was not context-local.** One LLM instance runs the worker
  and the auto-title call concurrently -- the reason `_RequestLocalProvenance`
  already exists -- so the shared start time and first-token map were attributed
  to whichever call read them first, and a concurrent title call could swallow
  the worker's measurement. It now lives in a context-local holder with the same
  deep-copy semantics.

The other four: the ledger's read-modify-write was unsynchronized and folding
was not idempotent (a failed directory removal left the session discoverable and
the next delete counted it twice); `permission="broad"` bypassed the attachment
guard because `check_path` short-circuits for it; the rate lookup matched
substrings, so a model the table does not cover would be charged another model's
rate; and the buffered sync-generator fallback stamped every chunk at stream
end, making "first token" latency the full latency.

One design change came out of the third finding rather than the review's
preferred fix: refusing a delete whose usage cannot be folded would leave an
operator unable to remove a session after a state-read failure. The gap is
written into the ledger instead (`unarchived`), and the delete is refused only
when the ledger itself cannot be written.

## Remaining limits

- **The attachment guards are path and content checks, not a sandbox.** A
  session's authority still comes from its permission preset and the workspace
  it was given; a symlink swapped between validation and read is the same race
  H1 documented for file reads.
- **Only images are supported**, and only as whole files: no PDFs, no remote
  URLs (by design), and no way to attach a file that lives outside the
  workspace.
- **Attachment versions are not frozen for snapshot tasks.** H4 pins the
  workspace revision; an attachment read from outside the pinned tree is read at
  dispatch time.
- **The ledger records tokens, not money.** It is priced at report time with the
  current table, so a price change re-prices history; a versioned price per
  recorded period is not implemented.
- **A failed fold leaves a gap, recorded but not repaired.** The ledger keeps
  an `unarchived` entry naming the session and the reason, and `tools/spend.py`
  reports how many there are, so the total says it is short rather than looking
  complete. Nothing re-derives the missing tokens.
- **First-token latency is only recorded for streamed calls**, and only when the
  chunk carries the token: a call that returns everything at once has no
  first-token timing, which reads as null.
- **No live end-to-end run was part of this pass**; the live gate remains an H7
  action alongside cutover.

## Rollback

H6 adds defaulted fields to `ConversationConfig`, `StoredConversation` and
`ConversationInfo`, and one additive metrics field, so legacy records still
load. The ledger is a new file; ignoring it restores the previous behaviour
exactly. Source rollback is a normal revert; do not run an older binary over
state after a future migration.
